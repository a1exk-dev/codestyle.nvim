# Language Plugins are runtimepath specs with lazy Lua modules

Each Language Plugin is a separate repo that ships one spec module, `lua/codestyle/languages/<id>.lua`. When the Core is first used, it finds every spec with `nvim_get_runtime_file(..., true)`, so installing the plugin is enough, and two plugins with the same language id are detected (ADR-0003). The spec is cheap data: the contract version `api`, the id, the display name, filetypes and an optional `match(buf)` predicate, the Tree-sitter language and Vim syntax names for the Preview, the Options, the Tabs with their Preview samples, the Presets (ADR-0006), and the key migrations. Code that is heavy or rarely used is named as module paths that the Core `require`s on first use: `formatter`, `scheme` (the PhpStorm field → Option mapping) and `arrangement`. So opening the Menu loads only data, and the first format loads the formatter ("What is the Language Plugin contract?", #12).

## Considered Options

- **An explicit list in `setup()`**, as with neotest adapters. Nothing is implicit, but every user must edit `setup()` for each language.
- **Self-registration** from each plugin's `plugin/` file. It depends on load order and breaks with lazy loading.
- **A semver range of the Core** in each spec. It couples plugins to Core releases that do not change the contract.
- **Plugins that `require` each other as Lua libraries** (Blade requires the HTML plugin). It is simpler, but it skips the Core's version check and its missing-plugin warning. IntelliJ shares the HTML rules by subclassing (`VueBlock extends XmlBlock`), which our design rules exclude.

## Consequences

- With lazy.nvim, the user lists Language Plugins as `dependencies` of codestyle.nvim, because a plugin that is not loaded yet is not on the runtimepath.
- The Core exposes one integer contract version, `require('codestyle').api`. Within one version the Core only adds optional fields and functions. A breaking change raises the version. The Core accepts the old version for one more Core minor release with a deprecation warning, then refuses the plugin with one warning that names it. Its stored values stay in the file (ADR-0001). The Core's own semver is separate.
- The `formatter` module has `build(ctx)`, which returns a tree of plain Block tables made with Core constructors, and `rules`, which the Core calls on the parent Block: `spacing(parent, left, right, values)` for a Gap that the parent owns, and `child_indent(parent, index)`. Rules get Blocks of another language as opaque Blocks. The Core offers a port of IntelliJ's `SpacingBuilder` as a helper. Each rule declares the parser nodes and fields it needs (ADR-0002).
- Optional steps are `formatter.before` and `formatter.after`, lists of `step(ctx) → edits`. With a selection, the Core drops an edit outside `ctx.range` with a warning. `formatter.format(ctx) → edits` replaces the Core engine for the language. Such a language has no Blocks, so it can be neither a host nor an embedded part, and its parts in other files are kept as written (ADR-0008).
- Arrangement runs first, returns edits and gets the same `ctx`. The rest of its shape belongs to the Arrangement design. `ctx.lsp(method)` returns the user's attached client or nil, and a feature that gets nil is skipped with one warning.
- A plugin that builds on another one declares `uses = { html = 1 }`. The Core then gives it the resolved values of `html` (`ctx.values.html`) next to its own and `general`, and the HTML plugin's exported handlers and rules (`ctx.uses.html`). A plugin that exports declares `exports = { version = N }`, with the same additive rule as the contract version. When a used plugin is missing or has another export version, the plugin is still listed in the Menu, but its formatting is off, with one warning that names both plugins. Options stay on their own language's Tabs (ADR-0003).
- The `scheme` module is import-only: entries that name the PhpStorm fields they read, an Option key, and an optional `from(fields) → value` for Options that join several fields. It also lists the fields of Options that v1 leaves out, so an import can tell "left out" from "unknown". The Scheme XML import and the golden tests use it.
- Migrations are idempotent and need no stored version: renames of keys and of choice ids. The Core applies them when it reads a file, moves a value only when the new key is not set, and writes the new keys at the next save.
- The Core ships `codestyle.testing`, a public module that is versioned with the contract. Plugin repos run it headless over the Behaviour Records and their Presets, with a list of expected failures.
